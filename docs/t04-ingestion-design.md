# T04 资料与导入设计

本文记录 T04 的需求澄清与设计决定。用户已接受两轮共七项建议，设计已达成共同理解，以下方案作为开发依据。未执行编译、启动、测试、导入或外部服务调用。

## 现有依据与任务边界

- 开发计划：[T04 资料与导入](06-parallel-development-plan.md)。代码范围为 `src/main/java/com/mango/backend/knowledge/ingest/**`，资料范围为 `data/**`。
- 共享契约：[T01 契约](08-t01-contracts.md)。实现 `KnowledgeTokenizer`，供导入与 T05 检索共同使用；复用既有模型、存储和快照类型。
- 存储行为：[T03 交接](09-t03-persistence.md)及 [ADR 0003](adr/0003-immutable-published-corpus.md)。向量请求位于数据库事务外；完整导入后发布 `READY`；失败快照保持 `BUILDING`，以新快照完整重导；保留旧快照，不修改已发布资料。
- 原文约定：保存完整原文，片段使用 UTF-16 半开区间定位；归一化仅影响索引文本。文档、片段和资料集合的哈希算法沿用 T01。
- 业务边界：第一版使用合成报销与差旅制度；版本日期不代表适用优先级，主题标签不能编码冲突结论，替代关系必须有原文支持。
- 验收前提：[E01/E02/E04/E05/E08](../examples/cases.json)分别需要明确期限、未消解冲突、相似改写、差旅凭证追问与文档替换材料。E01 与 E02 的问题相同、资料前提不同，必须区分资料快照。

访谈起始时，当前分支为 `dev`，HEAD 为 `7845d25`；该提交仅记录核查起点，实际开发基线在创建任务 Worktree 时确定。

## 第一轮已确认

用户已接受以下三项建议。

1. **资料组织**：提供明确规则、冲突规则和资料替换三组独立完整资料集合，分别导入为独立快照。明确规则包含 30 天期限及差旅凭证等条款；冲突组增加 15 天规定，双方不声明适用范围、优先级或替代关系；替换组只改动期限条款，便于后续核对答案是否随资料变化。
2. **导入入口**：提供显式执行、执行后退出的命令行批处理入口。接收资料 JSON 文件路径，沿用现有数据库和模型配置，成功后输出快照标识与文档、片段数量；导入不随问答服务启动自动执行。
3. **条款组织**：合成原文采用统一的「第 X 条」编号，导入器按完整条款切分，保留条款内适用条件；每条显式标注中性主题。JSON 结构、文首说明归属及过长条款处理见第二轮决定及下文实施约定。

## 代码与配置核查

只读子代理已完成相关契约、T03 存储实现与文件资产核查，主代理核对了相关类型和配置。以下为静态事实，不代表运行验证结果。

- 当前没有 `data/`、导入器或 `KnowledgeTokenizer` 实现。已有 jieba 1.0.2 依赖，默认使用内置词典且不启用额外停用词。
- Embedding 默认单批最多 32 条，单条最多 4000 个 Java 字符，调用超时 15 秒；数据库单次超时默认 5 秒。超限由现有客户端明确拒绝，不截断文本。
- 导入的文档批次、片段批次分别提交短事务。后续失败时，已写入的批次保留在 `BUILDING` 快照中；已有恢复规则是用新快照完整重导。
- 最新问答资料按 `READY` 快照的发布时间选择，因此导入完成并发布后，后续新问答会使用这份快照。现有契约没有另设激活或问答指定快照参数。
- 发布检查文档数、片段数和文档集合哈希；片段与原文的一致性由 T04 在导入边界检查。
- `KnowledgeTypes` 已规定排序、UTF-16 偏移、UTF-8 SHA-256 及集合哈希格式；T04 沿用这些约定。

## 第二轮已确认

用户已接受以下四项建议。

1. **JSON 输入**：每份文件保存完整文档列表；每个文档含 ID、版本、版本日期、标题、适用范围、替代关系、完整原文，以及「条款编号 → 中性主题」的标注。片段 ID、偏移和哈希由导入器生成。拒绝未知字段、类型错误、重复键或重复标识，不自动修正输入。
2. **不符合格式的条款**：规则及适用条件均写入编号条款；文首只允许标题行与空白。拒绝缺失编号、主题标注不完整、空条款或超过 Embedding 单条配置上限的条款，并指出文档和条款。完整文件在数据库写入和模型请求前完成本地校验，不自动拆散或截断条款。
3. **分词默认值**：首版提供内置 jieba 词典、不启用额外停用词的默认配置；落实已有自定义词典、停用词路径配置，资源指定后不可读取或格式不合法则明确失败。索引处理保留中文、数字及有意义的字母词元；导入与查询复用同一实现。
4. **命令执行语义**：每次执行生成新的快照 ID；同一文件再次执行也完整重建。沿用默认批量及单次超时，顺序执行且不自动重试；另设默认 10 分钟、可通过命令行覆盖的导入总预算。全部完成后自动发布，影响后续新问答；输出快照 ID、资料集合哈希及数量，失败返回非零退出码，已创建时保留快照 ID 供定位。

## 实施约定

以下细节落实已确认的范围，字段和参数命名作为 T04 的内部约定；不修改 T01 的公共 Java 契约。

### 交付文件与模块

| 路径或能力 | 交付内容 |
| --- | --- |
| `data/corpus/normal.json` | 明确规则的完整资料集合。 |
| `data/corpus/conflict.json` | 包含双方期限规定的完整资料集合。 |
| `data/corpus/mutation.json` | 修改期限后的完整资料集合。 |
| `data/README.md` | 文件格式、合成资料声明、导入步骤、场景对应关系和待授权验证说明。 |
| `knowledge/ingest/` | JSON 导入边界、条款切分、jieba 分词、导入协调及命令行入口。保持单 Maven 模块，仅按清晰职责组织实际需要的类型。 |
| 本文及 `GLOSSARY.md` | 设计、交接与业务术语；实施中有符合记录条件的技术问题时补充 `docs/pitfalls/T04-*.md`。 |

主代理负责实现，子代理负责静态代码审查。T05 通过已有 `KnowledgeTokenizer` 接口使用本任务的 Spring Bean，不复制分词逻辑。导入入口单独加载导入、配置、模型客户端及持久化依赖，以非 Web 模式运行，不依赖 T07 提供 `QaService`。

### JSON 输入

顶层对象只包含非空的 `documents` 数组。每份文件都是完整集合，不把其他资料文件或旧快照当成隐式依赖。示例只演示一份文档，不代表最终资料数量：

```json
{
  "documents": [
    {
      "documentId": "D01",
      "version": "v1",
      "versionDate": "2026-01-01",
      "title": "费用报销制度（合成资料）",
      "applicableScope": null,
      "supersedes": [],
      "content": "费用报销制度（合成资料）\n\n第1条 报销申请应在费用发生之日起 30 个自然日内提交。\n\n第2条 申请报销应提交对应费用的有效凭证。\n",
      "clauseTopics": {
        "1": "报销期限",
        "2": "报销凭证"
      }
    }
  ]
}
```

- 文档 ID、版本、标题和原文必须是非空白字符串；版本日期使用有效的 `YYYY-MM-DD` 日期。原文保留反序列化后字符串的全部字符，不去除首尾空白、不替换换行、不做 Unicode 归一化。
- `applicableScope` 为字符串或 `null`，`null` 表示未知；`supersedes` 为明确替代对象的数组，元素沿用 `DocumentRef` 的 `documentId`、`version`。首批三组资料均不声明替代关系，冲突双方的适用范围均未知。
- `clauseTopics` 的键为原文条款的正整数编号字符串，值为非空白的中性主题；每个条款恰有一个主题标注，不接受不存在的条款标注。同主题使用相同值，保证两份期限规定能够被主题扩展同时发现。
- 使用导入专用的严格 JSON 读取配置，拒绝重复 JSON 字段、未知字段、尾随 JSON 值、类型强转、重复文档版本及重复条款编号。错误指出字段或文档、条款标识，不回显完整原文。
- 文档键、条款与主题覆盖、元数据及替代引用的结构在输入边界集中校验；不宣称结构校验能证明原文语义、制度效力或答案支持性。合成资料中的适用条件、替代关系和主题语义仍须在资料编写及静态审查中核对。

### 原文切分与标识

- 首批资料统一以行首的 `第1条`、`第2条` 等正整数编号标记条款，编号按原文顺序从 1 连续递增。条款标题、正文及其必要条件均保留在对应条款范围中。
- 第一条之前只允许与文档标题一致的标题行和空白；可影响制度含义的说明必须写成编号条款，避免文首条件未被检索。
- 片段从本条编号起始位置延伸到下一条编号起始位置，末条延伸到原文末尾。保持子串原样，使用 UTF-16 的 `[startOffset, endOffset)`；不添加标题、不拼接其他条款、不裁掉范围内空白。
- `chunkId` 由条款编号生成，例如 `clause-1`；同一份输入重导时，除 `snapshotId` 外的文档与条款标识保持一致。哈希及排序遵循 T01。
- 空条款或超过 `embeddingTextCharacters` 的完整片段直接拒绝，错误包含文档及条款标识；不以截断或自动拆分改变制度条件。

### 三组资料与验收交接

| 资料集合 | 主要内容 | 对应计划场景 |
| --- | --- | --- |
| `normal` | D01 规定费用发生之日起 30 个自然日内提交；D03 提供差旅事前审批、凭证等独立条款。 | E01 明确答案、E04 相似改写、E05 上下文追问；作为 E06 等失败场景的资料前提。 |
| `conflict` | 保留正常组资料，增加 D02 的 15 个自然日规定；与 D01 使用同一期限主题，双方不说明适用范围、优先级或替代关系。 | E02 冲突与补充查证。 |
| `mutation` | 保留正常组其他规则，将 D01 期限改为 20 个自然日并更新对应版本元数据；新快照不再包含 D01 的旧版本。 | E08 文档替换。 |

三组均不含股票期权资料，供 E03 核对资料外问题。日期与数值均属于明确标记的合成制度，不引用真实公司制度或用户隐私。

每次命令只导入指定的一个文件。E01、E04 和 E05 使用同一正常快照；E02 使用冲突快照；E08 先使用正常快照，再导入替换组。由于服务选择最新发布快照，执行场景时要按需要的资料集合顺序导入，不能把三个快照都发布后假定各请求会自行选择对应场景。

T04 在 `data/README.md` 中提供静态文档、条款和主题对应表。快照 ID 由真实导入产生，运行结果、Trace 和检索标准标注仍由后续验收记录，不在当前阶段预填或伪造。

### 分词与索引配置

- 默认使用现有 jieba 1.0.2 内置词典，停用词配置为空。保留词元顺序和重复次数，过滤纯空白、纯标点词元；索引中的字母统一使用与区域无关的小写，保留中文、数字、否定词和期限单位。
- 向量输入使用原始条款文本；索引处理仅影响分词副本，不修改存储原文、片段偏移或哈希。
- 自定义词典与停用词通过现有配置指定本地文件或 classpath 资源；资源为空、不可读或格式不合法时明确失败。没有指定路径时使用已确认的默认行为。
- 启用自定义资源时使用与实际资源对应的版本标识，不能仍将自定义词典标为 `builtin-v1`，或将非空停用词标为 `none-v1`。导入与查询使用相同资源及版本；配置改变后重建资料快照。
- 不改动既有公共接口，不为导入和查询分别维护预处理逻辑。

### 命令执行与失败反馈

命令接收必填参数 `--corpus-file=<JSON 文件路径>` 和可选参数 `--import-timeout-ms=<正整数毫秒>`，导入总预算默认 `600000` 毫秒。可复制的实际启动命令在实现交接时补入 `data/README.md`，明确标注尚未运行验证。

1. 读取并严格校验完整输入，生成文档、片段、词元及各级哈希。输入不合法时不创建快照、不发模型请求。
2. 为本次尝试生成新的 UUID 快照标识，建立 `BUILDING` 快照，写入实际使用的 `IndexProfile`。
3. 分批写入文档；按现有批量上限顺序请求 Embedding，每批响应通过 T02 的模型边界校验后，将向量、词元和片段一起写入。向量请求位于数据库事务外。
4. 完整导入后以预期文档数、片段数和集合哈希调用 T03 发布接口，在短事务中切换为 `READY`。
5. 成功时输出 `snapshotId`、`contentHash`、`documentCount` 和 `chunkCount`。已发布快照随即成为后续问答的最新资料；正在执行的问答继续使用原快照。

总预算从导入协调开始计时，使用单调时钟，在本地准备及各依赖调用前后核对。单次 Embedding 和数据库调用的预算取剩余时间与既有单次配置上限的较小值，不把问答总预算直接当成导入总预算；不足以启动新调用时停止。数据库连接获取的既有限制沿用 T03，不额外承诺比底层连接等待更严格的瞬时中断。

失败返回非零退出码，输出错误类别、固定说明及可用的文档、条款或快照标识；不输出密钥、连接密码、上游原始响应或整份资料。创建前失败说明未创建快照；发布前失败的快照保持 `BUILDING`。若发布调用的响应本身失败，则提示以快照 ID 查询实际状态，不声称能撤销数据库中可能已经完成的发布。无自动重试、补写、删除或断点续传；再次执行创建新快照。

### 开发、审查与交接

开发顺序为：三组资料与严格输入边界 → 完整条款切分 → 共享 jieba 分词 → 导入协调与命令行接线 → 文档与静态审查。实现使用现有依赖、配置、模型及持久化接口；若发现必须调整共享文件的事实，再明确受影响范围，不在当前方案中预设额外架构。

按仓库规则，新建任务 Worktree，由主代理完成代码；调用子代理静态审查，修复后合并 `dev`，确认合并结果后删除任务 Worktree。编译、启动、依赖树、测试、数据库初始化和真实导入均等待用户后续指令。

交接说明记录实际基线、任务分支、修改文件、审查结论、已知限制及 T05 调用方式。待授权验证覆盖严格输入、条款子串与哈希、分词与资源加载、三组资料导入、失败快照隔离、发布清单及非 Web 命令退出；静态审查不表述为这些验证已通过。
