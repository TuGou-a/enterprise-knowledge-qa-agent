# T09：并行补查被错误判为未执行

## 现象

Java 17 真实 E02 运行 `d9e73d43-1121-462a-99ad-f0f5560cb2cf` 返回正确的
`CONFLICT/APPLICABILITY_UNKNOWN`，并完整引用 D01、D02，但新增验收断言在
`RealQaEvaluationTest` 第 129 行失败，报告“Expecting actual not to be empty”。

Trace 显示模型在同一模型轮次连续发起 D01、D02 和 D03 `clause-1` 的读取，其中 D03 的公开目的为
“确认差旅报销制度的适用范围”。D03 是读取原文形式的合法补充查证，但断言没有识别。

## 环境

- macOS、Java 17.0.19、Maven 3.9.9、AgentScope 2.0.4
- DeepSeek `deepseek-chat`、硅基流动 Embedding／Rerank
- conflict 快照 `9fe4377e-b373-4187-b364-1165fc3e4766`

## 原因

测试先要求补充工具在双方读取完成之后“开始”。实际运行中，D03 的补充读取与 D01、D02 同轮并行开始，
其开始序号早于另一条读取的完成序号，但读取结果仍在双方结果之后交付并被模型观察。

验收要求是“读取冲突双方后至少补充查证一次”，不能把工具开始时间与读取完成时间直接比较。补充查证
既可以是 `SEARCH_KNOWLEDGE`，也可以是针对适用范围或替代关系的 `READ_KNOWLEDGE`。

## 解决方案

先按公开目的或有效参数找出适用关系、替代关系、优先级或废止关系相关工具的 callId，再仅接受
完成序号晚于双方读取完成、且没有交付错误和 `ToolError` 的结果。最终仍要求该结果之后存在一次
模型推理开始事件，保证模型实际观察到补查内容。

该顺序约束只修正验收断言，不改变产品输出或工具选择；它避免把合法的并行读取误判为缺少补查。

## 验证

修正后的断言经两位子代理静态审查后，以合并提交 `87c48bb` 进入 `dev`。Java 17.0.19 下重新运行
真实 E02 连续 `3/3` 通过，运行 ID 为
`1a896ff6-2e5d-402e-9235-9a5b54d3efb6`、`9f492d8a-f32e-47ad-939b-6c0361285951`、
`ecf4ff6c-a7e8-44ff-ad22-ebf4ae8f839f`。三次均在双方读取后成功完成适用关系或替代关系补查，
接着进入后续模型调用，并以 `CONFLICT/APPLICABILITY_UNKNOWN` 结束。
