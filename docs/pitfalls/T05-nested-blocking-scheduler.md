# T05：同步工具等待同一线程池的内部任务

## 现象

静态接线审查识别出一种风险：并发问答较多时，检索工具已占用共享工作线程，但内部召回任务一直排队，最终返回路由超时，即使数据库与模型服务可用。该场景尚未通过运行测试复现。

## 环境

项目采用 Java 17、AgentScope Java 2.0.4 与 Reactor。框架同步业务工具运行于共享 boundedElastic 工作线程，T05 的同步 `KnowledgeSearch.search` 需要等待两个并行召回分支汇总。框架调度约定见 [方案说明](../02-solution.md)，T05 设计见 [检索与读取](../t05-search-design.md)。

## 原因

如果外层工具占用共享 boundedElastic 线程并通过 `block()` 等待，而召回分支又通过同一共享调度器启动，当外层调用占满线程上限时，内部任务只能排队。若没有超时兜底，这种相互等待可能形成死锁；当前路由的 `timeout` 会在预算截止后结束等待，因此表现为阻塞到时限并返回超时，仍会让并发检索失效。工具数量设为顺序执行只约束同一次问答，不能阻止多个问答并发占用线程。

这是依据同步等待与有限线程池关系作出的静态判断，尚不代表实测并发阈值或超时频率。

## 解决方案

T05 的 `HybridSearchService` 为内部召回创建独立 boundedElastic 调度器，沿用 Reactor 的默认线程及排队容量，在组件销毁时通过 `@PreDestroy` 释放。父调用与内部任务不再争用同一有限工作线程集合；内部任务仍只产生各自结果，账本由主调用统一写入。

并行路由继续受共同工具截止时间及请求预算约束。独立线程池不能保证阻塞数据库或 HTTP I/O 在取消时立即终止，实际取消效果和并发容量仍需用户授权后运行验证。
