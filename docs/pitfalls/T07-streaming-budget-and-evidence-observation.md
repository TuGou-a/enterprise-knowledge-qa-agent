# T07：流式调用总时限与证据观察顺序

## 现象

静态接入核查发现两种容易误判为正确完成的情况：流式模型持续返回片段时，每个片段都可能重置空闲超时；模型在同一轮请求读取原文和生成最终草稿时，引用可能已登记，但模型尚未看到读取结果。

## 环境

Java 17、Spring Boot 3.5.10、AgentScope Java 2.0.4，使用 DeepSeek 非思考模式和框架合成结构化输出工具。核查依据为本地参考仓库 `v2.0.4`，未运行模型、编译或测试。

## 原因

`Flux.timeout(Duration)` 限制的是相邻信号的间隔，不能单独提供一次完整流式调用的总时限；即使总请求时限存在，单次模型调用仍可能超过配置的能力时限。

发行版 `ReActAgent.dispatchToolCalls` 先执行同批普通工具，再执行 `generate_response`。结构化工具的参数由此前同一次模型调用生成，所以执行顺序不能证明模型已经观察原文。仅按最终证据注册表检查引用存在，会漏掉这一时间关系。

## 解决方案

模型边界同时收紧框架调用超时，并通过独立定时信号限制完整事件流，外层结构化 `Mono` 再限制请求剩余时长。持续收到文本不能延长这两项总时限。

把已读证据与已观察证据分开：原文成功读取后由 T05 登记；收到框架工具交付事件后关联真实 callId；实际模型调用开始时，从该次输入中确认已交付读取结果，固定可供该轮草稿使用的证据键集合。原始草稿中已登记且原文匹配的引用若不在该集合中，整体拒绝为 `INCOMPLETE/OUTPUT_INVALID`，不追加自动修复调用。必须在 T06 可能整体清空引用前保留这一事实，避免另一条无效引用掩盖观察顺序违规；不存在或原文不匹配的引用仍按 `CITATION_INVALID` 处理。此前已观察的片段在同轮重复读取，不因此失效。

取消与超时后的迟到事件不得继续写入本次已封存 Trace。以上为源码分析和实现方案；真实流式超时、工具事件顺序及取消行为仍待用户授权运行验证。

静态审查还发现，模型在截止前返回并不代表其后的输出校验也在截止前完成。最终结果组装必须重新读取权威预算快照，按实际限制标志覆盖草稿终态，并让响应与 Finished 共享该快照，防止出现 `ANSWERED` 与 `deadlineExceeded=true` 同时返回。SDK 以其他异常包装超时时，Trace 分类检查 cause 链中的超时类型，仍使用固定的脱敏说明。
