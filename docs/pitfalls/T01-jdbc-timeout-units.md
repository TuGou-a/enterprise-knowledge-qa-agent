# T01：剩余预算与 JDBC 超时的单位差异

## 现象

定义数据库交接契约时发现：请求剩余预算采用毫秒或 Duration，而 JDBC/MyBatis 语句超时采用整秒。直接把不足一秒的剩余预算换算为 0，可能把「预算即将耗尽」变成「不设置查询超时」。这是静态设计核查识别的风险，尚未观察到运行故障。

## 环境

Java 17、Spring Boot 3.5.10、MyBatis starter 3.0.5；问答总预算建议初值 120 秒，数据库能力级上限 5000 毫秒，MyBatis 默认语句超时 5 秒。T01 只冻结接口与配置，数据库实现归 T03，尚未运行验证。

## 原因

JDBC 查询超时的单位为秒，0 表示不限制；直接对正的亚秒 Duration 向下取整会得到 0。反过来向上取整为 1 秒，又可能超过剩余总预算。外层取消 Reactor 订阅也不能据此保证同步数据库查询立即终止。具体驱动、连接池及事务的超时覆盖关系仍待实际验证。

## 解决方案

T03 接收已取能力上限与剩余预算较小值的 Duration，在数据库边界向下换算为正整数秒；不足一秒时不开始新查询，返回明确预算错误，不传入 0。T07 保留整体截止时间，T03 同时配置语句、驱动和连接池超时；不能只依赖外层取消。授权测试后再核对真实 PostgreSQL 的阻塞、超时与取消行为，当前不宣称这些组合已生效。
