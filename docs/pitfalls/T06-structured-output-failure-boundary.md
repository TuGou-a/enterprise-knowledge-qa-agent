# T06：结构化输出失败与模型运行失败的边界

## 现象

仅将 null 草稿交给输出校验器，无法区分模型请求失败、模型调用前完整输入超限，以及模型已返回但内容无法解析。若统一解释为输出无效，会丢失 `MODEL_FAILED` 或 `INPUT_LIMIT_EXCEEDED` 等真实原因。

这是静态契约核对发现的风险，尚未通过编译、运行或测试复现。

## 环境

项目使用 Java 17、Spring Boot 3.5.10 及声明的 AgentScope Java 2.0.4。`dev@ccdda70` 中，`AnswerValidator.validate` 仅接收 `AnswerDraft` 与 `RunContext`；上下文提供预算、证据、检索聚合及 Trace，没有单独的模型终止状态。后续 T07 负责真实框架接线，运行兼容性尚待验证。

## 原因

`AnswerDraft` 是反序列化完成后的业务对象。非法 JSON、非法枚举等问题可发生在进入校验器之前；请求失败和调用前拒绝也可能都不产生草稿，因此不能从草稿缺失推导唯一的失败原因。

`BudgetSnapshot.textLimitExceeded` 表示累计读取/工具文本预算受限，不是每次完整模型输入的长度检查结果。用该字段兼容两种限制会混淆预算含义。将未发起的调用写成已失败模型轮次，也会让 Trace 与实际执行不符。

## 解决方案

用户已确认沿用现有共享签名：T07 在模型请求或输入预检边界处理真实失败，按完整优先级生成未完成结果；模型成功返回但内容不能解析时，T07 向 T06 传 null 草稿，由 T06 在没有更高优先级限制时解释为 `OUTPUT_INVALID`。

T06 只处理草稿及上下文中已有的可信预算和检索事实，不扫描 Trace 反推模型状态，不信任模型自报的运行失败。Trace 保留实际事件。T07 接线时仍须验证总超时、预算、模型失败和解析失败并存时的优先级，相关决定见 [T06 设计记录](../09-t06-output-validation-trace.md)。
