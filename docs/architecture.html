企业知识问答 Agent

面向报销与差旅制度。先以向量和关键词寻找候选，再通过重排序确定阅读顺序；Agent 查证原文，输出回答、引用与明确的任务状态。

考核优先Java 17 · Spring BootAgentScope Java 2.0.4 · MavenMyBatis · PostgreSQL · pgvectorjiebaDeepSeek · SiliconFlow
01双路召回→02RRF 融合→03BGE 重排序→04原文查证→05带引用回答
技术路线依据需求讨论确定。表结构、接口与参数是实施建议；文档中的流程演示不是运行记录。当前业务工程尚未接入 Agent、检索或云模型。

问题和历史由调用方提交。制度带文档 ID、版本日期与原文。首期覆盖报销、差旅规则，保留未知适用范围。

OUTPUT / 输出

回答、原文引用、资料缺口与状态

明确回答依据。冲突时展示双方资料；无法确认时追问；达到执行上限时明确返回未完成。

02技术选型与取舍

选择原因按实际约束记录。完整说明同步写入 README，便于答辩与后续复核。

选择为什么选择代价与适用边界
Java 17已确认 · 个人经验我更熟悉 Java，现有工程也是 Spring Boot 与 Maven，便于在有限时间内实现、排查和测试。部分 AI 示例优先提供 Python 版本，需核对 Java 生态能力。不是通用的语言优劣结论。
AgentScope Java已确认 · 时间约束开发时间有限，希望聚焦业务开发，复用模型适配与工具循环，减少底层大模型交互代码。固定发行版；理解框架上限、事件与结构化输出行为，业务质量仍由项目验证。
PostgreSQL＋pgvector已确认 · 简化部署一个数据库保存原文、版本、关键词索引与向量，减少组件和数据同步工作。应用实现召回 SQL、融合与一致性。规模扩大后重新测试召回和性能。
MyBatis已确认 · 数据访问Mapper 接口与 XML 集中管理原文入库、版本读取、向量与全文查询，直接表达 PostgreSQL 特有 SQL。维护 SQL 和结果映射；绑定查询参数，校验向量转换。3.0.5 为候选版本，目标工程仍需验证。
混合检索＋RRF混合已确认 · 融合方式为建议向量覆盖相似表达，关键词覆盖明确术语；按排名融合，形成重排序候选池。需要 Embedding、查询与评估。不能预先声称混合一定优于单路。
BGE 重排序已确认 · 硅基流动 API使用 BAAI/bge-reranker-v2-m3 联合比较问题与候选条款，细化相关性排名，复用已有云端服务。增加请求延迟、费用和文本传输；失败时回退 RRF。分数不能确定制度效力或回答可信度。
jieba Java已确认 · 中文分词在 Java 进程内完成中文分词，给 PostgreSQL 提供词项，文档与问题共用处理配置。验证词典、停用词、版本与并发行为；关键词排序用 ts_rank_cd，不是 BM25。
DeepSeek＋硅基流动已确认 · 云端模型DeepSeek 决策与回答；硅基流动提供 Embedding 和重排序，本地只运行应用与数据库。依赖网络、账号可用性与限流条件。三类能力分别配置、校验响应与记录耗时。
单 Agent、调用方历史单 Agent 为建议 · 历史方式已确认一个 Agent 通过检索与读取工具完成任务，便于观察决策；请求带历史即可覆盖上下文追问。调用方负责传回历史。首期不提供服务端跨请求会话恢复。

框架和模型能力见 官方来源；数据库选型另记录为 ADR-0001。

04混合检索与重排序

召回扩大资料覆盖，RRF 合并排名，Reranker 细化相关性。其他制度版本单独保留，最终由 Agent 读取原文并查证适用关系。

20＋20两路召回上限
20RRF 后送入重排序
6主候选上限
＋12主题扩展上限

以上均为待验证初值，可按资料规模和评估结果配置。topK 仅控制主候选，主题扩展另计，累计文本仍受请求预算限制。

为什么保留 RRF，再做重排序

RRF 以排名合并两路不同量纲的分数，形成覆盖较广的候选池；Reranker 联合比较问题与条款，细化池内顺序。先保留最多 20 条，再选最终主候选，避免过早缩小到 6 条。

RRF(d) = Σ 1 / (60 + rank(d))

为什么单独扩展其他版本

30 天与 15 天的条款都可能与问题相关。按重排序前候选池的 topic_key 补充其他版本，独立返回，不以分数阈值过滤。存在截断时显式披露，不能声称已穷尽规定。

RRF 分数、重排序分数均不是回答置信度。

两条候选仅用于展示请求结构，实际 top_n 等于融合候选池大小。取得完整分数后，本地按分数、RRF 名次与稳定片段键排序，再选取 topK。BGE 不发送 Qwen 专用的 instruction。

  1. 保留输入映射输入下标对应快照、文档版本与片段键。
  2. 验证返回值检查 index 范围、唯一性、数量和有限分数；并列按 RRF 排名与片段键排序。
  3. 按本地原文查证结果只调整阅读顺序，不修改知识库，不代替 readKnowledge。
执行结果应用返回的排序模式后续行为
重排序成功RERANK返回主候选与独立主题扩展，Agent 继续读取。
重排序超时、限流或响应异常RRF_FALLBACK整批回退 RRF，记录降级原因；召回与查证完整时允许披露降级后回答。
候选池为空NONE / SKIPPED_EMPTY跳过云请求，由 Agent 判断是否补查；空候选本身不等同于无依据。
必要召回失败或主题查证截断另记 unresolvedErrors / truncated继续保留材料，通常返回 INCOMPLETE；已读取并证实的冲突可同时披露。

配置与预算：重排序建议超时 10 秒，实际不超过请求剩余总预算；调用前检查候选与文本长度，不静默删去适用条件。更换 Reranker 无需重建文档向量，但需要重新评估。来源：硅基流动 Rerank API、BAAI 模型卡。

05Agent 动态决策

检索和读取由模型选择，工具结果回到模型。补充检索、追问和停止都必须基于本次观察。

预期路径对比

下列交互为设计示意，用于说明行为差异，不是真实模型输出或已通过的测试。

明确答案：找到依据后结束

预期状态：ANSWERED
  1. 选择检索模型以「报销期限」检索，工具返回相关制度候选。
  2. 选择读取模型读取支持答案的指定版本条款。
  3. 检查依据是否充分模型根据条款回答，提供原文引用和必要条件。
  4. 校验并结束应用校验本次证据与引用后返回结果。

必要检索完成、关联主题未截断，且已读资料没有冲突时，可以按 D01 回答；检索预览必须进一步读取核对。

06资料与版本模型

将原文、制度版本与检索配置绑定，确保一次请求的回答和引用来自同一份资料快照。

保持引用原文不变

分词、大小写和全半角处理只用于索引。原文保留字符范围与哈希，建议使用 Java UTF-16 索引区间验证 substring 一致性。

小数据先做精确向量检索

全文索引使用 GIN，版本与主题使用普通索引。HNSW 可以后续加入；先保证资料召回与可复现性，再依据性能结果调整。

07接口与工具契约

拟定问答接口 POST /api/qa，复用现有 Result<AnswerEnvelope>。下文展示接口概览；T01 定稿类型、配置与恢复规则见 契约交接文档，运行结果尚未验证。

searchKnowledge(query, topK)

分别返回主候选与关联版本，包含预览、两路排名、RRF 分数和重排序分数（若有）。topK 由服务端夹取至 1 至 6，关联扩展最多另加 12 条；资料快照由应用注入。

readKnowledge(documentId, version, chunkId)

返回指定版本原文、字符范围和哈希，加入当前请求证据集合。版本不存在或读取失败时，返回明确的结构化工具错误。

{
  "question": "那差旅报销也是这个期限吗？",
  "history": [
    {"role": "user", "content": "普通费用报销期限多久？"},
    {"role": "assistant", "content": "<此前回答>"}
  ]
}

历史只接受 user 与 assistant，限制数量与总长度；超限明确拒绝。每个请求使用独立运行 ID 和 Agent 状态。历史不直接充当制度证据。

输出字段用途
runId / snapshotId由应用填充，定位本次运行与固定资料版本。
answer / status / reason模型提供业务草稿，应用校验后形成任务结果与结束原因。
citations[]文档 ID、版本、片段 ID 与实际原文，支持核对回答。
evidenceGaps[]明确缺少的资料、适用范围或必要背景。
clarifyingQuestion需要补充的信息，例如本次报销应适用哪份制度。
retrieval应用填充 routes、rankingMode、rankingWarnings、degraded、truncated、unresolvedErrors，区分排序回退与必要召回失败。
budget实际轮次、业务工具调用数与超时信息；Embedding 和 Rerank 是检索工具内部调用，纳入总超时。
任务状态适用情况
ANSWERED已有本次读取的资料支持回答。
NEEDS_CLARIFICATION缺少必要背景，先请求补充。
CONFLICT存在现有资料无法消解的制度冲突，保留双方引用。
NO_EVIDENCE在当前已完成的查找范围中缺少充分依据，说明缺口。
INCOMPLETE上限、超时、工具或模型失败、无效输出导致未完成。

HTTP 状态和 Result.code 表达接口处理情况，status 表达任务结果；资料冲突和无依据不应被包装成「成功回答」。

08引用、冲突与失败

明确哪些约束由代码检查，哪些结论仍需要模型判断和效果评估。

EVIDENCE / 证据

引用必须真实存在

校验快照、已读片段、版本与原文。ANSWERED 需要支持引用，CONFLICT 至少引用双方已读版本；NO_EVIDENCE 需要已完成相关检索且主题未截断。

CONFLICT / 冲突

有分歧就查证适用关系

D01 的 30 天与 D02 的 15 天不能凭日期或排名取舍。查不到适用范围、优先级或替代关系时，展示冲突并请求确认。

FAILURE / 失败

区分排序回退与召回失败

重排序失败可回退 RRF，查证充分时披露降级后回答；Embedding 等必要召回未恢复或主题被截断时，通常返回未完成。错误不伪装成空结果。

BUDGET / 预算

预算由服务端强制限制

建议 maxIters＝6、业务工具最多 12 次、总超时 120 秒，均为待验证初值。包装层原子计数，并限制候选、读取和输入长度；触发上限返回未完成。

两项评估边界：字符串一致只能证明引用存在，不能证明答案受其支持；向量检索返回近邻，也不能证明问题在资料范围内。两者均需要用例和语义核对。

框架达到 MAX_ITERATIONS 后可能追加汇总，应先检查结束原因，不能把汇总标为成功。Trace 保存工具参数、结果摘要、后续动作与公开依据，不保存密钥或内部思维。历史与制度正文不能覆盖系统约束。

PERSISTENCE / 数据访问

MyBatis Mapper 管理查询与映射

CorpusMapper 管理快照，DocumentMapper 管理版本原文，ChunkMapper 管理入库、两路召回、主题扩展与读取。XML 位于 resources/mapper/knowledge/；服务层负责事务、RRF 与重排序协调，云 API 调用在数据库事务外执行。

HybridSearchService→ChunkMapper→Mapper XML→PostgreSQL
查看向量查询映射示意
<select id="searchByVector" resultType="ChunkCandidate">
  <![CDATA[
  SELECT document_id, version, chunk_id, topic_key,
         embedding <=> CAST(#{queryVector} AS vector) AS distance
  FROM kb_chunk
  WHERE snapshot_id = #{snapshotId}
  ORDER BY distance, document_id, version, chunk_id
  LIMIT #{limit}
  ]]>
</select>

映射为说明草案，需注册结果别名。向量先校验 1024 维与有限数值，再序列化为绑定参数；tsvector 在 SQL 内构造。查询值均通过 #{queryVector} 等占位符绑定，每条 SQL 都限定快照；排序表达式固定。XML 使用 CDATA 或转义处理比较运算符。

硅基流动：两类检索能力分别校验

发行版行为需要注意：2.0.4 的结构化调用使用 call(..., 输出类型, RuntimeContext)，DeepSeek 默认走工具回退；streamEvents 没有同样的结构化类型重载。使用中间件记录调用事件，先检查最大轮次退出原因，再解析结构化结果。详见 接入核查。

2.0.4 在汇总失败时也保留 MAX_ITERATIONS，并标记 SUMMARY_FAILED；应用仍返回未完成。generate_response 是框架内部工具，不增加第三个业务工具。真实 Trace 需证明读取完成后模型再次推理，不能把同轮预先生成的最终草稿当作已观察原文。

完整环境变量模板见 .env.example。Spring Boot 不会默认自动读取根目录 .env，需由终端、IDE 或容器注入。本次文档未使用真实密钥调用服务。
